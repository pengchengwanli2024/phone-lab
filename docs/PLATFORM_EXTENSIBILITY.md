## 2026-11-17 经营总控与复查实施契约

`commerce/operating_pipeline.py`以原商品工作项、精确`case_id/platform/store_ref/market/goal`为范围，投影ProductWorkspace、原组织门禁及当前目标上架方案。`commerce_operating_pipeline_get`只读返回能力实现状态、业务验收状态、依赖、来源引用、缺项、责任岗位和可接续工具参数；不会采集、调用模型或创建经营任务。`goal=launch/operate/brand`分别选择必要阶段，上架准备不依赖尚不存在的订单或结算。完整链路目标见主需求2026-11-17补充。

资料/供应/媒体原门禁PASS仅作为本地完整性/币种/哈希检查；不提升成真实市场结论、供应商、商品身份或权利验证。当前新总控不签发经营成功：`business_outcome_verified=false`。广告、客服、采购、物流监控索赔、结算和品牌的真实执行缺口保留。跨市场/平台不得沿用原门禁作为目标验证；目标规则与负责人核查从当前上架方案读取，不把Ozon/RU的case签收复制给其它站点。

读取返回`snapshot_sha256`；准备动作可带`expected_snapshot_sha256`拒绝变化。`commerce_operating_pipeline_template`必须核对该SHA，输出原ExtensionRuntime兼容的只读工作流定义、scope/input/budget，不保存、测试、启用或运行。使用原`commerce_extension_save/test/enable/run`及可选interval schedule。唯一新增SAFE_BUILTIN为只读get，运行器逐次校验case、platform、store_id与market；goal固化在版本化定义中，不开放其它经营工具。每调度槽创建新的原运行/原任务，按槽去重，旧回执保留；重复旧幂等键不会产生新观察。

流程自身succeeded仅表示本次诊断已读取，不能作为上架/采购/广告/发货完成。源/草稿变化需重新判断；未知平台结果优先保持unknown，不能以新草稿过期覆盖并重发。同时检查精确目标的历史申请，较新申请不能遮住旧申请的未决回执；每轮最多核查200条，超限明确保留unknown，不推断没有更早未决项。失效的可选素材关联仅形成该阶段缺项，不遮住其它经营阶段；库存快照门禁不等于采购/付款/发货就绪。输出只投影证据ID/哈希、状态和缺项，不复制原始客户资料或凭据。空闲复查不调用模型，实际外部经营动作仍沿原业务执行器、策略与授权。

### 行为与权限

- 工单由调用者明确创建，绑定 project、源码文件清单、允许写路径、固定检查、任务类型、模型快照和预算；同幂等键不同输入拒绝。工程执行账本从属于原 tasks，不复制业务事实。
- 三个阶段为 Planner、Builder、Reviewer；模型通过现有无工具推理生成类型化计划、文件修改、审查结果。宿主校验并在私有快照写入修改；模型不能提供命令或申请额外工具。Reviewer 只作模型审查，独立性及自动检查范围明确记录。
- 当前根目录无 Git。首版使用私有、逐文件哈希的源码快照，产出统一补丁；不初始化用户 Git、不提交推送、不自动回写原项目。只复制明确批准的源码文件，拒绝隐藏/运行数据、凭据和软链接；AGENTS.md 作为只读约束加入上下文。
- 检查由宿主从固定 Python unittest/compile 配方构造；在已验证可用的操作系统沙盒中运行，禁止网络、读取用户私有目录及工作区外写入。沙盒不可用则 blocked，不降级为宿主裸跑。不可编辑验收文件；只有补充测试可在明确获准的新路径生成。
- 任务状态包括 queued/running/awaiting_review/failed/unknown/cancelled/interrupted；完成模型调用或检查成功不代表补丁已采用。取消覆盖本任务模型与检查进程；重启保留已落盘回执，将在途结果标为 interrupted/unknown，需明确恢复，不自动重发。
- 默认并发一个工程任务、最多两轮修复、五次模型调用、整体超时；额度在调用前预留。费用/Token 无真实回执时保持 unknown。全局停用阻止后续调用并取消当前工作。
- 项目记忆分为可追溯的运行经历、明确确认且绑定源码版本的工程经验、受版本管理的操作配方。过期/撤回经验不进入新任务上下文；历史仍可查询。经营事实继续使用原 LayeredMemory，工程经验不能变成店铺授权或全局助手规则。
- HR 先对已有失败与审查原因做确定性归类，优先建议测试/检查/API修复，再建议技能调整或新角色。输出候选，不能直接启用角色、修改权限或生成新业务任务。启用与原扩展版本/测试门禁衔接；结构验证不冒充行为改善评估。

### 实施与验收顺序

1. 独立模块与真实 SQLite/文件系统回归：幂等、路径/软链接边界、沙盒、源码漂移、预算、撤回/过期记忆、停止及重启。
2. 接入原 service/MCP、任务查询和可选后台 tick；隔离 Commerce 实例验证三阶段与原经营功能兼容，合成模型明确标识。
3. 通过真实可用模型处理一个本项目的有界源码任务，在沙盒运行原检查；产出补丁与来源证据，保持 awaiting_review，不修改日常源。
4. 本地常驻依赖现有独立服务生命周期。仅在源码冻结、现有任务空闲、备份和原记录核对后保护加载；持续时长只按实际观测报告，不宣称已证明 24×7。

### 首版入口、记忆与运行方式

实现位于 `commerce/engineering/`，经 `commerce_engineering_*` 接口和 `commerce/engineering_cli.py` 接入原共享服务。原 `commerce_task_result/cancel/retry` 识别工程所有权，不再交给经营执行器。三阶段各自记录实际提供方回执；Reviewer 是同一路线的另一次调用，不冒充独立认证。

使用项目现有 Python 环境：

```sh
python commerce/engineering_cli.py status
python commerce/engineering_cli.py enable
python commerce/engineering_cli.py submit work-order.json
python commerce/engineering_cli.py get <run-id>
python commerce/engineering_cli.py artifact <run-id>
python commerce/engineering_cli.py recall
python commerce/engineering_cli.py retrospect
python commerce/engineering_cli.py disable
```

`work-order.json` 必须包含 `goal`、`files`、`writable_paths`、`checks`、`idempotency_key`；可明确 `kind=bugfix/feature`、`model_id`、`max_attempts`、`max_model_calls`、`max_seconds`。`checks` 是 `{"kind":"python_unittest","paths":["tests/test_module.py"]}` 或 `python_compile` 配方，不接受命令文本。只有工单显式列出的文件进入快照，必须列齐依赖；缺依赖会失败，不绕到日常源码读取。bugfix 的原验收须实际失败，否则返回 `engineering_bug_not_reproduced`。

功能到验证的映射维护在 `commerce/engineering/features.json`，首批仅覆盖工程 CLI 和离线装箱候选。`commerce_engineering_feature_list/feature_get/prepare` 均为只读：不入队、不检查、不调用模型。配方经源码审查维护，不能通过工具动态扩大权限；目录返回 `verification_status=not_run`，登记本身不证明当前功能通过验收。可先检索/检查，再生成兼容原提交入口的工单：

```sh
python commerce/engineering_cli.py features
python commerce/engineering_cli.py feature engineering-cli
python commerce/engineering_cli.py prepare engineering-cli --goal "明确的修改目标" --key "本次唯一工单键" > work-order.json
python commerce/engineering_cli.py submit work-order.json
```

生成的 `feature_ref` 固定配方和源码哈希，包括只读 `AGENTS.md`；入队及执行前拒绝配方、文件范围和源码漂移。原幂等请求仍返回同一任务，不重复创建；不带 `feature_ref` 的显式手写工单保持兼容。已经完成的历史任务和经验不会被改写；依赖源码变化的经验按原规则显示 stale，不自动注入新任务。

默认关闭工程调度，启用本身不生成工单。已启用后由原服务时钟非阻塞派发；单工程任务互斥，日调用上限30（Asia/Shanghai）、单任务最多2轮/5调用/300秒。日额度和在途调用前预留均持久保存；队列等待不占本任务执行时长。结果未知不重发。检查器探测工作区外读写、网络、Shell、跨进程信号和fork拒绝，任何探针失败都不执行检查；独立watchdog在启动前落盘归属，宿主断开时回收检查进程。watchdog自身异常丢失时，以独立持久回执核对checker是否已终止；未核清则保留unknown，并阻止所有状态下的后续工程派发，不能用取消覆盖未知结果；允许读取当前基础Python发行版运行库，不开放整个用户目录。此为本机实测边界，不是形式化安全证明。

工单结果先为 `awaiting_review`。操作者审查并在原项目实际采用后，可调用 `commerce_engineering_record_adoption`，传入 `run_id/candidate_sha256/confirmed=true`；服务仅在全部候选文件哈希实际匹配时记录 `completed`，接口不改源码、不提交Git、不部署。补丁支持无终止换行的文件；运行经历和旧回执保留。

运行经历自动从原执行账本检索；工程经验通过 `commerce_engineering_memory_propose` 绑定原回执，再以准确SHA明确确认或撤回。未确认、源码变化或撤回的经验不进入新上下文；已采用任务的经验绑定实际候选。记忆只提供可解释上下文，不授予工具或修改用户全局助手记忆。业务事实继续由原 `LayeredMemory` 管理。

HR首版入口 `commerce_engineering_retrospect` 做零模型消耗的失败聚合、证据指向和改进候选；已有 `commerce_extension_assist` 可将明确选定的候选生成技能/Agent草稿。保存、测试、启用继续走原扩展门禁。尚未实现自动招聘、自动启用或以结构测试证明行为改善；需要基线/候选/保留案例的真实评估后再扩大自主权。

首个真实模型任务修复了新工程CLI“全量读取后才检查输入限额”的缺陷：实际3次Codex调用约42秒，原失败检查在沙盒中通过，操作者审查采用后记录completed，并保留一条绑定候选来源的经验。这证明有界开发回路可运行，不代表复杂工单收益或长期稳定性已验证。任务验收覆盖运行正确性、明确拒绝与重启恢复；验收数据为隔离状态，未发店铺/设备操作。

### 为什么值得继续做，以及投入边界

phone-lab已有多个宿主、经营模块和并行工作，重复定位入口、复述上下文、核对源版本、人工搬运错误和复验结果才是本团队优先消除的成本。长期资产是功能到验证的映射、可执行约束、带证据且能失效的记忆与可恢复的工单。组织图本身不构成收益。

继续扩大前，应记录每项实际采用结果、操作者复核时间、返工次数、未发现的缺陷及可知用量，与原人工协作方式比较。功能地图应复用既有页面/能力登记与QA入口；复杂并发状态先增加状态机与性质检查，再按实际需要考虑形式化工具。模型评估使用未参与提示词改写的保留案例，避免只优化评分；增加岗位须有重复的能力缺口证据。先工程再经营，保持业务权限、对象范围和事实验证的独立门禁。

持续时长及最终回归以本次私有验收回执为准；没有持续观测的数据不标为24×7验收通过。

## 项目资产与宿主选择（A07–A08、X01–X03、O01）

项目核心持久保存业务账本、项目记忆、技能/插件登记和执行回执，宿主通过统一接口读取最小任务上下文。项目记忆记录来源、对象/项目作用域、版本、观察时间、事实/推断、有效性和审阅状态；撤回或过期后不再作为当前依据，历史引用仍可解释。技能保存方法与输入/产物合同及版本，插件保存能力、依赖、适配版本、私有配置引用、启停及验收状态。三者不能仅存于宿主聊天或全局安装目录。

默认主执行端只能是 Harness、Hermes、Codex 之一。调度前按有效授权、真实能力与版本、健康、资源占用、任务适配及可知用量筛选，记录候选缺口和选择理由；用户指定时仍检查这些前提。运行平台与模型提供方分开登记，不能因选择 Hermes 就假定必须更换项目模型。其它客户端可查看同一业务，安装/打开状态不构成执行权。

同一任务的活动执行权由项目核心互斥保存，包含主执行端、尝试、租约/心跳及接管记录。宿主失联后先停止后续派发并核对原尝试、外部回执和设备占用；租约过期不证明外部动作未发生。仅在结果已核清且允许继续时接管原任务，禁止对 unknown 自动换端重发。独立任务与明确授权的专项并行遵守已有资源互斥，不把三选一扩成默认三端竞跑。

部署验收分别覆盖三端可接入、单端选择、并发抢占、失联/未知接管及项目资产备份恢复。当前共享接口、业务存储和静态目录可复用；统一调度、记忆管理及完整扩展生命周期仍待实现，不能由 MCP tools/list 通过代替。

## 1. 能力分层（X01）

| 类型 | 它提供什么 | 不应混同 |
| --- | --- | --- |
| 技能 / 方法 | 任务适用条件、输入、步骤、交付与复验要求 | 文档读取不代表工具、账号或执行器可用 |
| 工具 | 一次明确的类型化读取、计算或动作 | MCP 描述和注解不构成授权 |
| 执行器 | 持有本次范围、预算和取消权的实际运行单元 | 接受任务不等于完成业务；不允许来源内容直接执行命令 |
| 连接器 | 平台授权、资源读取/写入、字段与分页/水位转换 | 某一平台资源可用不等于该平台所有业务可用 |
| 模型提供方 | 明确的模型路线、支持的输出/媒体形式及用量回执 | 当前研发助手能调用不等于平台后台能调用 |
| 界面扩展 | 已登记的业务组件及声明式数据与动作 | 组件包不是独立业务数据库，不提供任意脚本注入 |
| 渠道 / 外部智能体 | 消息接收、通知、确认或有范围的任务委派 | 渠道身份、用户权限、任务归属和收件要分别校验 |

一个插件可打包以上多类能力，但每一项单独声明、测试和启用。当前助手会话可使用的第三方设计、图像或视频插件，不自动成为 phone-lab 运行时插件；如需接入，必须有独立适配、授权、数据范围及可恢复回执。

## 2. 统一能力登记（X01、X03）

首先登记现有内置能力，随后接外部适配。以下字段是平台内部目标合同，不宣称属于现行 MCP/A2UI/A2A 标准字段。

| 字段组 | 最少内容 |
| --- | --- |
| 身份与来源 | `capability_id`、类型、名称、版本、维护者、来源/包哈希、许可和变更摘要 |
| 业务适用性 | 平台/市场/经营模式、任务类型、前置输入、限制、输出产物类型 |
| 调用合同 | 输入/输出 schema、执行器引用、只读/本地写/外部写分类、幂等语义及批量边界 |
| 权限和数据 | 所需授权作用域、可读取字段、出站目的、敏感字段投影、数据留存及对象范围 |
| 资源控制 | 最大耗时、模型/请求/并发/文件额度、已知计费方式、超额行为、取消检查点 |
| 生命周期 | 安装/配置/启用版本，凭据有效性、能力探测、兼容宿主、健康与降级结果 |
| 结果核验 | 来源及测试版本、离线/合成/真实回执、检查器、外部回读方法、未知处理和补救方式 |
| 界面贡献 | 受支持组件目录、配置字段、可读状态、已有页面入口；不注册任意脚本和私有业务状态 |

“撤销”必须说明撤销的是权限、后续调度、已生成产物还是外部动作；无法撤销的平台动作不能展示通用“撤销”按钮。回退插件版本也不能承诺撤回已经发生的经营行为。

## 3. 能力可用性与任务匹配（X01、X02）

保留多条状态轴：来源完整性、执行器可用、账户/数据就绪、验证范围、当前健康。不能用一个绿色“已安装”覆盖它们。

面向用户的能力页首先回答：**适合本次任务吗、现在能运行吗、还缺什么、会生成什么、需要哪些权限、有哪些已知限制**。其次再展示技能正文、工具 schema 和技术来源。

匹配顺序为：业务目标→平台/对象→输入是否齐全→账户与资源范围→执行器是否可用→版本与验证→用量和策略。模型只能从通过这些约束的候选中选择；不把全部工具或797项原文同时放入上下文，也不凭标题相似替代适用性检查。

现有 SeaLeap 保留 797 项顶层、19 个专用离线入口、778 个草稿准备入口与227个细分模式。推荐优先补齐高频路径的领域检查器和真实输入样例；不以增加目录数量作为平台扩展成功指标。需要新技能时，先比较已有输入/产物契约，避免复制相同方法和任务。

目标能力还包括技能与工作流的创建/改编：从缺口建立草案，填写适用范围、输入、步骤、工具依赖、产物和检查器，提供合成样例，隔离试运行后审阅发布新版本。AI 可协助写草案和生成测试资料，不能自行安装执行代码、扩大权限或替换正在运行的版本。可复用流程保存为计划模板，实例化时重新绑定真实对象与有效能力；导入/导出仅携带合同和公开/合成样例，不携带凭据、真实资料或运行账本。

| 能力层次 | 界面能做的承诺 |
| --- | --- |
| 仅有方法 | 可读原文和准备资料，执行方式未接入 |
| 草稿执行器可用 | 可生成受限文字草稿，真实业务输入/输出仍需检查 |
| 离线脚本已验证 | 指定脚本、版本及输入样例通过，不代表完整技能或账户操作 |
| 真实资源已验证 | 指定账户、区域、资源、权限和时间下有真实回执，不外推其它资源 |
| 范围内启用 | 在已生效策略内可运行；仍需本次输入、来源、健康和额度检查 |

质量检查至少分 schema/引用检查、领域规则、人工适用性及真实结果。测试失败、HOLD、needs_inputs、unknown 均保留；模型自评不能替代独立检查器。

## 4. 接入、升级和停用（X03）

推荐生命周期：**发现 → 来源/许可核对 → 安装或登记 → 私有配置 → 能力探测 → 隔离合同测试 → 真实只读验证 → 启用指定范围 → 观察与升级/停用**。不要求每类能力都访问外部账户；纯离线计算按其类型完成适用步骤。

内部轮询、手动请求、定时器及后续 webhook 都转换为有稳定ID、发生/接收时间、来源、对象范围和版本的事件；外部事件另验签名、重放和身份。流程模板只订阅明确登记事件，不因安装扩展自动增加后台调度。

| 操作 | 用户看到什么 | 系统必须做什么 |
| --- | --- | --- |
| 添加扩展 | 功能、数据访问、运行方式、费用依据、前置条件及维护状态 | 不凭自然语言说明安装任意依赖或执行第三方脚本 |
| 保存配置 | 已保存与尚未验证分开 | 凭据只写受保护配置，不经模型、聊天、MCP参数或组件状态回显 |
| 探测/测试 | 明确只测哪些资源、合成还是真实 | 先执行无副作用探测；测试写入另需范围与测试对象 |
| 启用 | 店铺/对象/角色/计划、允许动作、频率和限额 | 默认关闭自动任务，启用不扩大为全局授权 |
| 升级 | 版本差异、合同/权限/数据迁移影响和测试结果 | 固定新版本验证；权限或输出含义变化重新审阅；旧任务保留旧版本 |
| 停用 | 新任务停止，活动任务处置及历史可读性 | 停止后续派发；只取消拥有且可取消的任务；结果未知进入核对 |
| 移除 | 配置、凭据、产物、业务引用的处置范围 | 不级联删除有引用的历史；数据清理由保留规则单独决定 |

暂不建设开放市场。首批扩展以现有内置模块的登记与合同自检为主，再按真实工作缺口接店铺资源、媒体工具、客服渠道、物流、广告或结算数据。商品数据、规则和素材授权随具体使用核对。

## 5. 智能体、技能与插件如何协作（A03–A06、X05）

1. 编排器根据目标建立计划版本，匹配既有岗位和产物契约。
2. 准备步骤按最小上下文读取证据，并检查输入、连接、额度和能力版本。
3. 角色可提出工具/技能组合；执行器再次核对业务身份、动作策略和来源前提。
4. 方法生成结构化结果，确定性工具进行数值和领域检查，产物存入原模块并返回稳定引用。
5. 计划按检查结果继续、请求补充、转人工或等待审阅；失败不得通过更换插件绕过限制。
6. 本地完成与外部提交分别留回执；平台终态需回读。外部结果未知时先核对原记录，不自动切换执行器重发。

并行只用于输入独立且不会争用同一对象的步骤；店铺资源、媒体槽、设备及文件分别互斥/限流。订单、财务数值和同一商品产物的版本提交由共享核心检查，不能以模型间“达成一致”替代事务或事实核对。

有模型自动计划时，记录计划的最大模型轮次、可调用能力、单轮及周期预算、停止条件和责任人。未返回可靠用量/费用的提供方显示未知或已核对的上限，不能填0或伪造费用。

设备是被明确选择的执行资源，不是所有 API 失败后的自动替代路径；平台和应用限制不会因接入手机而消失。iPhone XCTest 提示限制继续保留，电脑提示不混入采集原图。

四类通道共用项目采集/任务/证据存储；同一资料通过稳定来源标识及内容版本关联去重，保留各通道观察时间、样本及差异。读取、采集和指定操作各自验收；验证码、登录失效、设备忙或来源限制返回缺项/等待，不能生成成功回执。具体目标网站、App和动作清单按实际任务确定，不宣称任意网站或任意操作均支持。

## 7. 协议、宿主与生成式界面（X06）

协议实现与业务合同分开版本化。现有项目固定 MCP 适配器、A2UI 0.8 五组件快照子集及 A2A 0.3 轮询子集；不因外部规范演进就宣布当前兼容新版。

| 通道 | 目标职责 | 验收要求 |
| --- | --- | --- |
| 共享 HTTP / MCP | 领域工具发现和调用，传递稳定对象、版本与回执 | typed schema、权限、作用域、幂等、错误和真实工具调用；工具可见性与调用授权分别校验 |
| A2UI 或内部视图合同 | 用已协商组件呈现资料、计划、比较、审阅和结果 | 组件目录/大小/动作版本校验；不支持时降级；浏览器与 Harness 使用同一业务合同 |
| A2A | 有限的外部智能体发现、任务委派、查询和取消 | 可信身份、任务归属、能力和授权范围；明确支持的轮询/流式/推送，不把终态旧任务重新写入 |
| 渠道卡片 | 手机上查询、补充、决策和定位原工作 | 同一对象与确认绑定，消息去重；不假定渠道能渲染浏览器组件或改变原生聊天外观 |

本轮参考官方资料核对的是设计原则：MCP 区分 tools/resources/prompts；A2UI 的组件目录约定模型和渲染器可表达的组件；A2A 将上下文、任务和产物分别组织。这些原则支持本项目的分层设计，不表示已经安装新 SDK 或实现全部规范。[MCP 服务端概念](https://modelcontextprotocol.io/docs/2026-07-28/learn/server-concepts)、[A2UI 组件目录](https://a2ui.org/concepts/catalogs/)、[A2A 任务生命周期](https://a2a-protocol.org/latest/topics/life-of-a-task/)（查阅于2026-11-12）。

A2UI 官方页面本轮标示 v1.0；当前项目仍为0.8子集。是否迁移应依据目标宿主、所需组件、转换成本及合同回归决定，先评估再独立实施；不将追逐版本号列为业务完成条件。旧客户端保持明确兼容路径，不静默改变既有结果结构。

## 8. 扩展验收清单

### 模型、媒体与配置工作流的独立适配（2026-11-13，X07–X08、O06）

用户确认继续通过模块和插件扩展，首期优先模型选择、自定义和本地模型。宿主选择、模型推理、媒体制作、业务工作流和移动控制分层，均复用项目存储与任务/产物引用：

| 扩展 | 接入职责 | 独立验收 |
| --- | --- | --- |
| llama.cpp / vLLM | 已部署模型服务的兼容聊天API适配，提供模型ID、认证和输出能力 | 指定服务版本/硬件/模型实际推理、结构化结果、取消、资源与未知处理；测试通过不证明所有模型或原生工具调用可用 |
| 自定义模型服务 | 由用户保存可信基础地址和模型ID，按明确API合同增加适配 | 私有凭据、地址校验、能力差异、连接测试、启停及错误；API名相同不假定全部参数兼容 |
| ComfyUI | 图像/视频等媒体工作流执行器，固定工作流、节点、模型及输入版本 | 保存原prompt_id，分别处理排队/运行/失败/未知/产物；核输出文件、来源与工作项交接，不把入队当成片成功 |
| 类Langflow工作流配置 | 类型化节点的可视化图、校验/试运行/发布；可选外部引擎适配 | 原任务账本、节点/流程固定版本、条件/依赖/补充/审阅、取消与恢复；外部流程导入先映射已登记能力，不直接执行代码节点或安装任意节点包 |
| 独立移动管理端 | 远程连接项目控制面，对话/模型、任务、审阅、产物、扩展及已授权设备控制 | 可信设备配对、服务端身份/作用域、撤权、审计、失联/重复请求与控制互斥；目标客户端与真机专项验收 |

对话模型选择持久保存到项目会话，业务上下文与模型选择各自校验；每次请求固定配置快照，切换只影响后续请求。新模型保存后明确测试与启用，不自动发送业务资料。密钥仅由私有HTTP向导接收，SQLite和MCP只保留不可逆回显的状态/私有引用；不进入模型提示词、聊天、项目记忆和前端持久缓存。旧凭据引用可能被活动请求使用，清理与撤权要区分，数据库备份不等于凭据备份。

模型运行器继续由项目宿主校验工具范围和结果；llama.cpp/vLLM的结构化输出只是传输约束，不能授予工具执行权。媒体和配置工作流统一采用原任务/尝试/外部回执语义；导入流程或ComfyUI自定义节点不自动获得安装、文件或网络权限。移动端不持有模型提供方或店铺的长期密钥，远程入口部署前另验身份与网络边界，不将当前回环API直接暴露公网。

官方技术依据（查阅于2026-11-13）：[llama.cpp HTTP server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)、[vLLM兼容服务](https://docs.vllm.ai/en/stable/serving/openai_compatible_server/)、[ComfyUI服务路由与队列](https://docs.comfy.org/development/comfyui-server/comms_routes)、[Langflow流程运行API](https://docs.langflow.org/api-flows-run)。这些资料用于适配合同，不表示已安装或通过全部能力验收。

每个新能力提交时给出：适用场景、输入/输出、来源与许可、验证版本、权限/数据流、运行限额、幂等/取消/未知语义、检查器、宿主/界面降级、迁移/停用方案和未覆盖项。实现细节不必全部进入普通用户流程，但影响本次操作的范围、费用和结果限制必须可见。

通过标准是当前任务能以可核对输入产生合格产物，并能解释失败及继续路径。静态技能导入、插件连接成功、工具发现、合成测试、真实只读和外部写入分别留证，不合并为单一“全部支持”。
